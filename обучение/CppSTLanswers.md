# Ответы на вопросы о контейнерах STL

## 1. Основные категории контейнеров в STL
Последовательные: vector, list, deque, array, forward_list
Ассоциативные: map, set, multimap, multiset
Неупорядоченные ассоциативные: unordered_map, unordered_set, unordered_multimap, unordered_multiset
Контейнеры-адаптеры: stack, queue, priority_queue

## 2. Разница между последовательными и ассоциативными контейнерами
Последовательные хранят элементы в линейном порядке, где положение каждого элемента определяется временем вставки и явно заданной позицией. Ассоциативные автоматически организуют элементы по ключу, обеспечивая быстрый поиск. 

## 3. Контейнер-адаптер
Контейнер-адаптер предоставляет специализированный интерфейс для базового контейнера. Например, stack (стек), queue (очередь) и priority_queue (приоритетная очередь). Они ограничивают доступ к элементам определённым способом, следуя конкретной структуре данных.

## 4. Разница между упорядоченными и неупорядоченными контейнерами
Упорядоченные контейнеры (map, set) хранят элементы в отсортированном порядке, используя сбалансированные деревья поиска. Неупорядоченные (unordered_map, unordered_set) используют хеш-таблицы, обеспечивая быстрый доступ O(1) в среднем случае, но не гарантируют порядок элементов.

## 5. Временная сложность для vector и list
Vector: 
- Доступ: O(1)
- Вставка/удаление в конец: O(1) амортизированно
- Вставка/удаление в середину: O(n)

List:
- Доступ: O(n)
- Вставка/удаление (при наличии итератора): O(1)
- Поиск: O(n)

## 6. Эффективность vector vs list
Vector эффективнее для:
- Произвольного доступа к элементам
- Последовательного обхода (лучше локальность кэша)
- Когда редко нужны вставки/удаления в середину

List эффективнее для:
- Частых вставок/удалений в произвольных позициях
- Когда важно сохранять итераторы при изменении контейнера

## 7. Сравнение производительности set и unordered_set
Set: поиск, вставка, удаление - O(log n), элементы всегда отсортированы
Unordered_set: поиск, вставка, удаление - O(1) в среднем, O(n) в худшем случае

Set предпочтительнее, когда:
- Нужен отсортированный порядок элементов
- Требуется предсказуемая производительность
- Операции с диапазонами

Unordered_set лучше при:
- Частых операциях поиска/вставки/удаления
- Когда порядок элементов неважен

## 8. Сложность вставки в середину vector и list
В vector: O(n), так как нужно сдвигать все элементы после точки вставки и возможно перераспределить память.
В list: O(1), так как нужно только перенаправить указатели соседних узлов, без перемещения других элементов.

## 9. Инвалидация итераторов
Инвалидация итераторов происходит, когда операция с контейнером делает существующие итераторы недействительными.

Для vector:
- Перераспределение памяти инвалидирует все итераторы
- Вставка/удаление инвалидирует итераторы после точки изменения

Для list/map/set:
- Только итераторы, указывающие на удалённые элементы, становятся недействительными

## 10. Амортизированная сложность push_back в vector
Означает, что отдельные операции могут требовать O(n) времени (при перераспределении памяти), но в среднем на большом числе операций стоимость одной операции стремится к O(1). Это достигается стратегией увеличения ёмкости (обычно в 1.5-2 раза), что делает перераспределения памяти всё более редкими.

## 11. Внутренняя реализация map и set
Обычно реализованы как красно-чёрные деревья или АВЛ-деревья, которые являются сбалансированными бинарными деревьями поиска. Это обеспечивает логарифмическую сложность для основных операций и сохраняет элементы в отсортированном порядке.

## 12. Реализация unordered_map и unordered_set
Реализованы на основе хеш-таблиц. Используют хеш-функцию для распределения элементов по "корзинам". При коллизиях (когда несколько элементов имеют одинаковый хеш) элементы хранятся в цепочках, обычно в виде связанных списков.

## 13. Когда выбрать deque вместо vector
Deque предпочтительнее когда:
- Требуются эффективные вставки/удаления как в начало, так и в конец
- Нужен произвольный доступ к элементам
- Важно избежать перераспределения памяти при изменении размера
- Контейнер будет очень большим, что может вызвать проблемы с выделением непрерывного блока памяти

## 14. Когда использовать multimap вместо map
Multimap используется, когда необходимо хранить несколько значений, связанных с одним ключом. Например, для словаря, где одному слову соответствует несколько определений, или для списка тегов, где один элемент может иметь несколько категорий.

## 15. Код для подсчёта частоты слов
```cpp
std::unordered_map<std::string, int> countWords(const std::string& text) {
    std::unordered_map<std::string, int> frequencies;
    std::istringstream iss(text);
    std::string word;
    while (iss >> word) {
        frequencies[word]++;
    }
    return frequencies;
}
```

## 16. Реализация LRU-кэша
```cpp
template<typename Key, typename Value>
class LRUCache {
private:
    int capacity;
    std::list<std::pair<Key, Value>> items;
    std::unordered_map<Key, typename std::list<std::pair<Key, Value>>::iterator> cache;

public:
    LRUCache(int cap) : capacity(cap) {}
    
    Value get(Key key) {
        if (cache.find(key) == cache.end()) {
            throw std::out_of_range("Key not found");
        }
        items.splice(items.begin(), items, cache[key]);
        return cache[key]->second;
    }
    
    void put(Key key, Value value) {
        if (cache.find(key) != cache.end()) {
            items.erase(cache[key]);
        } else if (cache.size() >= capacity) {
            cache.erase(items.back().first);
            items.pop_back();
        }
        items.push_front({key, value});
        cache[key] = items.begin();
    }
};
```

## 17. Аллокатор в STL-контейнерах
Аллокатор отвечает за выделение и освобождение памяти для хранения элементов контейнера. Все STL-контейнеры принимают аллокатор как шаблонный параметр, что позволяет использовать пользовательские аллокаторы. Пользовательские аллокаторы могут быть полезны для специфических случаев управления памятью, например, для использования разделяемой памяти или для отслеживания/профилирования использования памяти.

## 18. std::initializer_list и инициализация контейнеров
std::initializer_list - это легковесный объект-представление, который обеспечивает доступ к массиву константных значений. Он позволяет инициализировать контейнеры списком значений в фигурных скобках:
```cpp
std::vector<int> v = {1, 2, 3, 4, 5};
```
Контейнеры имеют конструкторы и методы (например, insert), принимающие initializer_list, что делает синтаксис более удобным.

## 19. Перераспределение памяти в vector
Когда vector исчерпывает выделенную ёмкость, он выделяет новый, больший блок памяти, копирует существующие элементы в новый блок, а затем освобождает старый. Стратегии увеличения ёмкости различаются между реализациями:
- GCC обычно использует множитель 2
- MSVC использует 1.5
- Clang часто придерживается GCC

Эта стратегия обеспечивает амортизированную сложность O(1) для операций добавления в конец.

## 20. Малая оптимизация строки (SSO)
SSO - это оптимизация, при которой короткие строки хранятся непосредственно в объекте string, а не в отдельно выделенной памяти. Это позволяет избежать дополнительных выделений памяти и улучшает локальность кэша для коротких строк, что значительно повышает производительность для частых операций с короткими строками.

## 21. Отличия std::array от C-массивов
- std::array имеет фиксированный размер, известный на этапе компиляции
- Знает свой размер через метод size()
- Имеет стандартные итераторы и методы STL
- Не преобразуется автоматически в указатель
- Можно копировать с помощью оператора присваивания
- Проверяет границы при использовании метода at()

## 22. Разница между reserve и resize в vector
reserve: выделяет память под указанное количество элементов, но не создаёт их. Размер не меняется, меняется только ёмкость.
resize: изменяет размер вектора, создавая или удаляя элементы по необходимости. Если новый размер больше ёмкости, также увеличивает ёмкость.

## 23. Гарантии исключений для операций с контейнерами
STL предоставляет три уровня гарантий:
- Базовая: не будет утечек ресурсов
- Сильная: если операция бросает исключение, состояние контейнера не меняется
- Noexcept: операция не бросает исключений

Разные операции имеют разные гарантии. Например, push_back в vector имеет сильную гарантию, если элементы удовлетворяют определённым требованиям.

## 24. Прокси-объекты в контейнерах (vector<bool>)
std::vector<bool> - специализация, которая хранит булевы значения в упакованном виде (один бит на значение). При доступе к элементу возвращается не реальная ссылка на bool, а прокси-объект, который имитирует поведение ссылки. Это может приводить к неожиданному поведению, если код ожидает настоящую ссылку.

## 25. Новые контейнеры в C++11 и позже
- C++11: array, forward_list, unordered_map, unordered_set, unordered_multimap, unordered_multiset
- C++14: не добавлено новых контейнеров
- C++17: string_view (не контейнер, но "контейнероподобный"), node handles для ассоциативных контейнеров
- C++20: span (тоже не контейнер, но "контейнероподобный")

## 26. Перемещающие конструкторы и операторы присваивания
Они позволяют "переместить" ресурсы (например, динамически выделенную память) из одного объекта в другой без копирования данных. Для контейнеров это означает, что мы можем перемещать большие структуры данных с O(1) сложностью вместо O(n) для копирования, что значительно повышает производительность.

## 27. Преимущества emplace_back и других emplace_*
Функции emplace_* конструируют объект непосредственно в памяти контейнера, избегая создания временных объектов и их копирования/перемещения. Это особенно эффективно для сложных объектов, когда создание временного объекта дорого.

## 28. Structured binding с std::map и std::pair
Позволяет распаковать пары или структуры на отдельные переменные:
```cpp
std::map<std::string, int> m = {{"one", 1}, {"two", 2}};
for (const auto& [key, value] : m) {
    std::cout << key << ": " << value << std::endl;
}

auto [it, success] = m.insert({"three", 3});
```

## 29. Объединение векторов без дубликатов
```cpp
std::vector<int> merge(const std::vector<int>& a, const std::vector<int>& b) {
    std::set<int> unique_elements;
    unique_elements.insert(a.begin(), a.end());
    unique_elements.insert(b.begin(), b.end());
    return std::vector<int>(unique_elements.begin(), unique_elements.end());
}
```

## 30. Реализация deque с помощью двух стеков
```cpp
template<typename T>
class TwoStackDeque {
private:
    std::stack<T> front_stack;
    std::stack<T> back_stack;
    
    void balance() {
        if (front_stack.empty()) {
            size_t half = back_stack.size() / 2;
            std::stack<T> temp;
            for (size_t i = 0; i < half; ++i) {
                temp.push(back_stack.top());
                back_stack.pop();
            }
            while (!temp.empty()) {
                front_stack.push(temp.top());
                temp.pop();
            }
        }
    }

public:
    void push_front(T value) {
        front_stack.push(value);
    }
    
    void push_back(T value) {
        back_stack.push(value);
    }
    
    T pop_front() {
        if (front_stack.empty()) balance();
        T val = front_stack.top();
        front_stack.pop();
        return val;
    }
    
    T pop_back() {
        if (back_stack.empty()) {
            // Аналогично balance(), но для back_stack
        }
        T val = back_stack.top();
        back_stack.pop();
        return val;
    }
    
    bool empty() {
        return front_stack.empty() && back_stack.empty();
    }
};
```

## 31. Проблемы производительности std::list
List имеет плохую локальность кэша из-за распределения элементов по отдельным узлам в памяти, что приводит к частым промахам кэша при обходе. На современных CPU это может привести к значительному падению производительности, особенно для больших списков. Векторы обычно намного эффективнее для последовательного доступа даже при наличии нескольких вставок/удалений.

## 32. Преимущества/недостатки хранения указателей в контейнерах
Преимущества:
- Меньше копирований больших объектов
- Полиморфное поведение через виртуальные функции
- Избегание проблем с инвалидацией ссылок при реаллокации

Недостатки:
- Необходимость управления памятью (утечки или двойное освобождение)
- Снижение локальности кэша
- Невозможность использования стандартных алгоритмов напрямую
- Потеря преимуществ value semantics

## 33. Резервирование памяти (capacity) в контейнерах
Capacity (ёмкость) - это количество элементов, которое контейнер может хранить без перераспределения памяти. Резервирование правильного количества памяти заранее (reserve) позволяет избежать дорогостоящих перераспределений при вставке элементов, что значительно улучшает производительность. Особенно важно для vector, где перераспределение копирует все элементы.

## 34. Short String Optimization и производительность std::string
SSO позволяет хранить короткие строки непосредственно в объекте string, избегая выделения памяти в куче. Это значительно улучшает производительность для строк до определенной длины (обычно 15-22 символа) благодаря:
- Отсутствию выделений/освобождений памяти
- Лучшей локальности кэша
- Меньшему количеству косвенных обращений к памяти

## 35. Использование пользовательских типов с unordered_map и unordered_set
Для пользовательских типов необходимо предоставить хеш-функцию и оператор сравнения на равенство:
```cpp
struct Person {
    std::string name;
    int age;
    
    bool operator==(const Person& other) const {
        return name == other.name && age == other.age;
    }
};

namespace std {
    template<>
    struct hash<Person> {
        size_t operator()(const Person& p) const {
            return hash<string>()(p.name) ^ hash<int>()(p.age);
        }
    };
}
```

## 36. Требования к типам в контейнерах STL
Базовые требования:
- Все: деструктор, копирующий конструктор, оператор присваивания
- Последовательные: конструктор по умолчанию
- Упорядоченные ассоциативные: оператор сравнения (<)
- Неупорядоченные ассоциативные: хеш-функция и оператор равенства (==)

C++17 ослабил некоторые требования для неполных типов и movable-only типов.
