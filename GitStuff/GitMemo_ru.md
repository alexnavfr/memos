## **1. Ответственность и действия разработчика**  

### **1.1. Управление собственными ветками**  
Разработчик обязан:  
- Своевременно удалять ветки, влитые в `main`.  
- Финализировать отложенные изменения (через мердж или аннотированные теги).  
- Следить за актуальностью своих веток.  

#### **Команды для разработчика:**  

**1. Удаление влитых веток:**  
```sh
# Проверить, что ветка влита в main
git branch --merged main  

# Удалить локально (безопасно, если влита)
git branch -d feature/my-feature  

# Удалить на сервере
git push origin --delete feature/my-feature
```  

**2. Финализация отложенных изменений:**  
```sh
# Если изменения готовы, но не вливаются сейчас – создать аннотированный тег
git tag -a postponed/feature-name -m "Отложено: причина (например, 'ожидание тестов')"  

# Отправить тег на сервер
git push origin postponed/feature-name
```  

**3. Проверка активности веток:**  
```sh
# Посмотреть дату последнего коммита в ветке
git show --quiet feature/my-feature  

# Список своих веток (фильтр по автору)
git for-each-ref --format='%(committerdate) %(refname:short) %(authorname)' --sort=committerdate | grep "Ваше Имя"
```

## **2. Ответственность и действия релиз-менеджера**  

### **2.1. Контроль чистоты репозитория**  
Релиз-менеджер обязан:  
- Организовывать периодическую очистку устаревших веток.  
- Напоминать команде о необходимости удаления ненужных веток.  
- Управлять аннотированными тегами для отложенных изменений.  

#### **Команды для релиз-менеджера:**  

**1. Автоматическая проверка старых веток:**  
```sh
# Список веток без коммитов >30 дней (напоминание для разработчиков)
git for-each-ref --format='%(committerdate:iso8601) %(refname:short)' --sort=-committerdate refs/remotes | grep -v 'main\|master' | awk 'BEGIN { threshold="'$(date -d "30 days ago" +%Y-%m-%d)'" } $1 < threshold { print }'
```  

**2. Принудительное удаление заброшенных веток:**  
```sh
# Перед удалением – согласование с командой!
git push origin --delete abandoned-branch  
```  

**3. Управление отложенными изменениями (теги):**  
```sh
# Создать аннотированный тег с описанием причины
git tag -a on-hold/feature-X -m "Приостановлено до Q2 2024 (блокирующий фактор: интеграция с API)"  

# Отправить все теги на сервер
git push origin --tags  
```  

**4. Автоматизированные напоминания (пример для CI/cron):**  
```sh
# Скрипт для ежемесячного оповещения в Slack/email
git for-each-ref --format='%(authorname) %(refname:short) %(committerdate:relative)' --sort=-committerdate refs/remotes | grep -v 'main\|master' | mail -s "Старые ветки для проверки" team@example.com
```

### **Примечания:**  
- Разработчики должны **еженедельно** проверять свои ветки.  
- Релиз-менеджер проводит **ежемесячный аудит** и рассылает отчет.  
- Теги `postponed/` и `on-hold/` требуют **обязательного описания причины**.  

Формат: **`<тип>/<название>-<дата>`** (например, `on-hold/payment-api-2024-03-15`).
